In this assignment, I implemented two MCP servers for my task manager project; one for reading and writing to files and another for retrieving and updating tasks. One decision I made while writing my tools for the database was to use an input schema consisting of an enum instead of a free-text field. I did this to prevent any potential prompt injections and also to stop any null or vague status fields from being inserted into the status column for a certain task. Although an enum prevents a user from updating a status with a malicious value, it could also throw errors when a user mistypes a valid enum value such as 'open' or 'in progress', causing it to be rejected.

Unlike calling a REST API, the MCP approach is different in the sense that Claude Code has direct access to the tools, services and files. An MCP approach allows a user to tell Claude to read or write to a file using a custom tool. The disadvantage of this approach is that it has wide access to a large amount of files, which could allow a malicious attacker to perform destructive writes to multiple files.

An API approach forces a user to tell Claude to repeatedly call a function to fetch a status code. Although an API approach can repeatedly test and call a function to see if it works, it cannot cover all test cases. Additionally, a status code could be manipulated for a certain endpoint, which could wreak havoc on the entire project.

One capability I wished my custom server had is the ability to count the number of tasks that belong to a certain status. This would be very helpful because it would allow me to view how many tasks are still open, how many are still in progress, and how many are completed. I can implement this tool by writing a schema that counts the number of tasks that correspond to the inputted status. From there, I can write a query to count all tasks that correspond to the status and return their count if it is possible.
